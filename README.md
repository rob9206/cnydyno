# Thunderhorse Tuning Website

V-twin specialists. All bikes welcome. Professional motorcycle dyno tuning
website for Thunderhorse Tuning (Dawson Motoring LLC) in Utica, NY. Powered by
DynoAI.

## About

Official website for Thunderhorse Tuning — a motorcycle performance tuning
shop offering in-house dyno tuning, mobile/event tuning across Central New
York, custom ECU calibration, and performance builds. Specialty is V-twins
(Harley-Davidson, Indian, Ducati); all bikes welcome.

## Architecture

This is a **pre-rendered static site** built from the Thunderhorse Tuning
Design System. Each route has its own `index.html` with fully rendered markup
and per-route `<title>`, meta tags, Open Graph, Twitter Card, and JSON-LD
structured data baked in at build time — so crawlers get complete content
without executing JavaScript. The same React components hydrate client-side
for interactivity (DynoAI VE calculator, booking form, dyno dashboard, SPA
navigation).

### Runtime files

- `styles.css` + `tokens/*.css` — design-system tokens (Voltage Red, Forge
  Black, Oswald/Barlow/JetBrains Mono, spacing, effects).
- `_ds_bundle.js` — compiled design-system React components (Button, Card,
  Input, Switch, Badge, StatReadout, Tabs, …), exposed on
  `window.ThunderhorseTuningDesignSystem_fe7e73`.
- `components/*.jsx` — source components (Nav, Home, Services, DynoAI, Booking,
  DynoResults, Status, StatusAdmin, SEO, shared helpers, App).
- `app.js` — precompiled client bundle generated by `_build/prerender.js`,
  loaded with `defer` and a content-hash query string (`?v=…`) for cache busting
  on each rebuild (no Babel-in-browser).
- `assets/logos/` — badge marks (red / cream / black / white).
- `assets/photos/` — real shop photography.

## Rebuilding the static HTML

The pre-render tooling lives in `_build/` (gitignored — local only). To
regenerate the route HTML after editing components:

```bash
cd _build
npm install
node prerender.js
```

This optimizes photo variants, rebuilds `app.js`, and re-renders
`index.html`, `services/index.html`, `dynoai/index.html`, `book/index.html`,
`dyno/index.html`, `status/index.html`, and `status/admin/index.html` from the
current component source. Commit the updated assets, `app.js`, and regenerated
HTML.

`node verify-deploy.js` runs a self-contained check that every route file,
asset, and referenced path is present and consistent.

### Focused booking rebuild and tests

The original `_build/` tooling is not tracked. For a booking-only change,
the tracked helper below compiles `components/Booking.jsx` into the existing
`app.js`, preserves all other compiled components, renders the booking page,
and refreshes the app cache key on all seven React entry pages:

```bash
npm ci
npm run build:booking
npm run check:booking
npx playwright install chromium --only-shell
npm test
```

Commit the generated files along with the source. The helper checks known
bundle/HTML boundaries and stops if they change. A later full prerender can
replace its output; it is not a general replacement for `_build/prerender.js`.
Browser tests load committed HTML and JavaScript from disk, serve React
locally, and mock every booking POST. They never submit to Netlify or Square.

### Booking validation and spam protection

The visible form uses one submit handler for clicks and Enter. It trims and
checks email syntax, reports accessible inline errors, rechecks the existing
date rules, and prevents simultaneous duplicate sends. The real hidden
`bot-field` is read from the form and a filled trap stops the request. The
deploy-time `booking-request` schema and existing Netlify URL-encoded field
names are preserved, as are Square, Calendly, and mailto fallback behavior.

These are **client-side checks**, not mailbox verification or a server-side
email validation guarantee. Direct HTTP requests can bypass JavaScript.
Netlify's documented Akismet filtering and registered honeypot remain the
server-side defenses; a successful HTTP response also does not prove a
notification was delivered or that an appointment is confirmed. No CAPTCHA,
email provider allowlist, or artificial wait is added for legitimate riders.

Before an authorized rollout, check the Netlify form detail page for the
registered `bot-field` extra spam protection, form detection, and notification
configuration. These dashboard settings have not been verified by the local
tests. After deployment is separately authorized, send one clearly labeled
request using a controlled real email address and confirm the stored fields,
Reply-To, and notification delivery. Check both verified and spam submissions.
Use a staging form to test direct malformed POSTs and honeypot rejection.
If nuisance submissions persist, consider Netlify-validated reCAPTCHA 2 or a
server-validated intake endpoint with protection against the legacy endpoint
being used to bypass it. Either requires separate implementation and platform
verification; adding a client CAPTCHA widget alone is not sufficient.

References: [Netlify form setup](https://docs.netlify.com/manage/forms/setup/),
[spam filters](https://docs.netlify.com/manage/forms/spam-filters/),
[troubleshooting](https://docs.netlify.com/manage/forms/troubleshooting-tips/).

For review without deployment, include `[skip netlify]` in both the commit
message and pull request title. Do not merge or remove those markers until
deployment is authorized. See [Netlify's skip-deploy behavior](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/).

## Live status portal

Customers get a text with a link like `/status/?t=<token>` and can watch their
bike move through dyno or storage stages in real time. The shop manages jobs at
`/status/admin/`. Both routes are `noindex` and disallowed in `robots.txt`.

**Architecture:** Netlify Functions (`netlify/functions/`) backed by Netlify
Blobs store job records keyed by unguessable capability tokens. The customer
page uses Server-Sent Events at `/api/status/stream?t=<token>` (auto-reconnect,
~1–2s updates) with a polling fallback to `GET /api/status?t=<token>`; the
admin console calls `/api/admin/jobs` with an `X-Admin-Key` header.

| Endpoint | Method | Auth | Purpose |
| --- | --- | --- | --- |
| `/api/status?t=<token>` | GET | token in URL | Customer-facing job view |
| `/api/status/stream?t=<token>` | GET | token in URL | SSE live job updates |
| `/api/admin/jobs` | GET | `X-Admin-Key` | List active jobs |
| `/api/admin/jobs` | POST | `X-Admin-Key` | Check in a new job (`{ patch }`) |
| `/api/admin/jobs?t=<token>` | PUT | `X-Admin-Key` | Update a job (`{ patch }`) |

**One-time Netlify setup:** In the Netlify UI, set the `STATUS_ADMIN_KEY`
environment variable to a long random string. Until it is set, the admin API
returns `503 not_configured` and the shop console cannot sign in.

**Shop workflow:** Open `/status/admin/`, sign in with the admin key, check in
a bike, then use **Copy customer link** and text it to the owner.

**Local dev with API:**

```bash
cd _build
node serve-api.js 8090
```

The local server uses `STATUS_ADMIN_KEY=thunder-dev-key` by default and stores
jobs under `_build/.local-blobs/` (gitignored). Open
`http://localhost:8090/status/admin/` to manage jobs and
`http://localhost:8090/status/?t=<token>` to preview the customer view.

## Deployment

Deployed on **Netlify** from this repo's `main` branch. `netlify.toml` sets
`publish = "."` with no server-side build step (HTML is pre-rendered locally
and committed). Clean-URL redirects (`/services` → `/services/`, etc.),
security headers (HSTS, X-Frame-Options, nosniff), and long-cache headers for
assets are configured there.

Other static hosts (Vercel, GitHub Pages, S3+CloudFront) work too — point
them at the repo root.
